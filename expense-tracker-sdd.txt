1. Project Overview
1.1 What the Application Is
Expense Tracker is an offline-first personal finance mobile application built with React Native (Expo) and TypeScript. It lets an individual record income and expenses, organize them into categories, set monthly budgets, and view spending patterns through reports and charts - entirely without an internet connection. The architecture is deliberately layered so that a future cloud-sync backend (Firebase or a custom REST API) can be added without rewriting the data or UI layers.

1.2 Problem Statement
Most people do not track day-to-day spending because existing tools are one of the following:

Problem	Consequence

Require constant internet / bank login	Fails in low-connectivity regions, raises
privacy concerns

Overloaded with features (investments, credit score, ads)

High cognitive load, slow onboarding

No offline-first guarantee	Data loss or blocked usage without signal
Poor category/budget UX	Users abandon tracking within days
No local data ownership	Users distrust cloud-only storage of financial data


Expense Tracker solves this by being fast, private, offline-capable, and focused exclu- sively on personal expense/income tracking.

1.3 Goals
• Enable a user to log a transaction in under 10 seconds.
• Work 100% offline with zero mandatory network dependency in Phase 1.
• Provide clear visual feedback on spending vs. budget.
• Keep all financial data on-device by default, encrypted where the OS allows.
• Be architected so cloud sync, multi-device support, and OCR/voice input can be added later without breaking existing screens or data.

1.4 Target Users
• Individuals who want a lightweight, private daily expense log.
• Students and early-career professionals managing a limited monthly budget.
• Freelancers/gig workers tracking irregular income and business expenses.
• Households wanting a simple (non-collaborative, Phase 1) budget tool.
• Users in regions with unreliable internet connectivity.

1.5 Use Cases
1. Quickly log a cash purchase after leaving a store.
2. Review "how much did I spend on Food this month?"
3. Set a monthly budget per category and get warned when nearing the limit.
4. Export a CSV of all transactions for tax filing or manual bookkeeping.
5. Back up all data before switching phones and restore on the new device.
6. View a pie chart of category-wise spending for the current month.
7. Track recurring bills as a special expense subtype (Phase 2).

1.6 Business Objectives
• Ship a Play Store-ready MVP within 8-12 weeks.
• Achieve high day-7 retention through frictionless entry (low-cognitive-load UX).
• Build a codebase that can later monetize via optional cloud-sync premium tier without a rewrite.
• Keep infrastructure cost at zero for Phase 1 (no backend required).

1.7 Benefits
• Privacy: no data leaves the device in Phase 1.
• Speed: local reads/writes are instantaneous - no network latency.
• Reliability: app is fully functional in airplane mode, on flights, in remote areas.
• Low cost: no server, no database hosting, no API bills for MVP.

1.8 Scope
In Scope (Phase 1 - MVP): Dashboard, Add/Edit/Delete Income & Expense, Categories (default + custom), Transaction History with search/filter, Monthly & Yearly Reports, Charts (pie/bar/line), Budgets per category, Settings (currency, theme, language stub), Dark Mode, CSV Export, Local Backup/Restore (file-based), Local Notifications (budget alerts, reminders).
Out of Scope (Phase 1): Cloud sync, multi-user accounts, bank/UPI integration, OCR re- ceipt scanning, voice input, AI insights, investments tracking, Wear OS/widgets. These are documented in the Future Roadmap.

1.9 Future Scalability
The app is built with a feature-based architecture and a repository pattern over storage (see Storage Design) so that:
• AsyncStorage can be swapped for SQLite (or run alongside it) without touching UI code.
• A SyncService interface can be implemented later to push/pull data to Firebase or a custom REST API (see API Readiness) using the same local-first data as the source of truth (offline-first, sync-when-available pattern).
• Redux Toolkit can replace Context API for global state if the app's state complexity grows (documented as an alternative in State Management).


2. Functional Requirements
Each feature below is documented with Purpose, Description, User Actions, Validation Rules, Edge Cases, and Acceptance Criteria.

2.1 Dashboard
Purpose: Give the user an at-a-glance summary of their current financial position.
Description: The Dashboard is the app's home screen, shown after splash. It displays: cur- rent month's total income, total expense, net balance, a mini category-wise pie chart, budget progress bars for categories with a budget set, and the 5 most recent transactions.
User Actions: - Tap "+" FAB to add a new expense or income. - Tap "See All" on recent trans- actions to go to full history. - Tap a budget progress bar to go to that category's detail/report.
- Pull to refresh (recomputes totals from storage). - Switch the displayed month via a month selector.
Validation Rules: N/A (read-only aggregation screen); all validation happens at data-entry screens.
Edge Cases: - No transactions yet ? show empty state with a "Add your first transaction" call to action. - All income, no expenses (or vice versa) ? chart shows single-segment or "no expense data" placeholder. - Negative net balance ? balance is shown in the "danger" color token. - Very large numbers (7+ digits) ? abbreviate (e.g., ?12.4L / $1.2M) with full value on long-press/tooltip.
Acceptance Criteria: - Given transactions exist for the selected month, the dashboard totals equal the sum of all expense/income records for that month, computed in = 100ms for up to 10,000 records. - Given zero transactions, an empty state is shown instead of a zeroed chart.

2.2 Income Management
Purpose: Let the user record money received.
Description: A dedicated "Add Income" form (visually distinct color from expense) captur- ing amount, date, source/category (Salary, Freelance, Gift, Interest, Other - customizable), payment method, and optional notes.
User Actions: Add, edit, delete an income entry; mark as recurring (Phase 2 flag reserved in data model now).
Validation Rules: - Amount: required, numeric, > 0, = 999,999,999.99, max 2 decimal places. - Date: required, cannot be more than 1 day in the future (configurable), defaults to

today. - Source/Category: required, must reference an existing category ID. - Notes: optional, max 500 characters.
Edge Cases: - Duplicate-looking entry (same amount/date/category within 60 seconds) ? show a non-blocking "possible duplicate" warning, do not block save. - Category deleted after being used by an income record ? historical record keeps a denormalized category name snapshot so history is not broken (see Data Models).
Acceptance Criteria: - Saving a valid income entry updates Dashboard totals and History list immediately (optimistic UI) without requiring app restart. - Invalid amount (0, negative, non-numeric) blocks save and shows inline field error.

2.3 Expense Management
Purpose: Let the user record money spent - the app's core feature.
Description: "Add Expense" form capturing amount, date, category (Food, Transport, Bills, Shopping, Health, Entertainment, Other - customizable), payment method (Cash, Card, UPI, Bank Transfer, Other), notes, and optional attachment placeholder (Phase 2: receipt photo).
User Actions: Add, edit, delete; duplicate an existing entry as a starting point for a new one; quick-add from Dashboard FAB.
Validation Rules: - Amount: required, > 0, = 999,999,999.99, max 2 decimals. - Date: required, cannot be in the future beyond today (configurable per user setting for post-dated entries). - Category: required. - Payment Method: required, defaults to last-used method. - Notes: optional, max 500 characters.
Edge Cases: - Deleting a category that has expenses tied to it ? expenses are reassigned to an "Uncategorized" system category rather than being deleted. - Editing an expense's date to a different month ? transaction must move correctly between monthly aggregates and reports. - Extremely high amount relative to history (e.g., >10x the user's monthly average)
? soft warning dialog, not a hard block.
Acceptance Criteria: - Deleting an expense removes it from all aggregates (dashboard, re- ports, charts) instantly. - Editing amount/date/category correctly re-triggers recalculation of monthly totals and budget consumption.

2.4 Transaction History
Purpose: Provide a complete, searchable, filterable ledger of all income and expenses.
Description: Infinite-scroll (virtualized) list grouped by date (Today, Yesterday, then date headers), each row showing category icon, title/notes, amount (color-coded income/expense), and payment method icon.
User Actions: Scroll, tap a row to view/edit detail, swipe to delete (with undo snackbar), search, filter, sort, multi-select for bulk delete.
Validation Rules: N/A (list/read screen).
Edge Cases: - 10,000+ transactions ? list must remain smooth via FlashList/virtualization and pagination (load 50 at a time). - Swipe-delete on the last visible item while list is scrolled
? maintain scroll position after removal.
Acceptance Criteria: - Deleting via swipe shows an "Undo" snackbar for 5 seconds before permanent deletion. - Filtering by category + date range returns correct results verified against a manual sum.

2.5 Categories
Purpose: Organize transactions for meaningful reporting.
Description: System ships with default categories (Food, Transport, Bills, Shopping, Health, Entertainment, Education, Groceries, Salary, Freelance, Gifts, Other). Users can add custom categories with a name, icon (from an icon picker), color, and type (income/expense).
User Actions: Add, edit, delete, reorder, archive (hide without deleting history) a category.
Validation Rules: - Name: required, 1-30 characters, unique per type (case-insensitive). - Icon: required, chosen from a predefined icon set. - Color: required, chosen from the design system's palette or a custom hex (validated as a proper hex color).
Edge Cases: - Deleting a category in use ? prompt: "Reassign N transactions to Uncatego- rized?" before allowing delete. - Default/system categories cannot be deleted, only archived (hidden from picker but still valid for historical records).
Acceptance Criteria: - Duplicate category name (same type) is rejected with inline error be- fore save. - Archived categories no longer appear in Add Expense/Income pickers but remain correctly labeled in historical transactions.

2.6 Monthly Reports
Purpose: Summarize a single month's financial activity.
Description: Total income, total expense, net savings, category-wise breakdown (table + pie chart), day-wise spending trend (line/bar chart), comparison vs. previous month (% change indicator).
User Actions: Change month via selector/swipe, tap a category to drill into its transactions, export this report as CSV/PDF (Phase 2 for PDF).
Validation Rules: N/A (read-only).
Edge Cases: Month with zero transactions ? empty state, no divide-by-zero errors in average calculations.
Acceptance Criteria: Sum of category breakdown equals the total expense figure shown at the top, always.

2.7 Yearly Reports
Purpose: Show annual trends across all 12 months.
Description: Bar chart of monthly totals (income vs expense), yearly category breakdown pie chart, best/worst spending month highlighted, average monthly spend.
User Actions: Change year, tap a month bar to jump to that Monthly Report.
Edge Cases: Partial year data (e.g., app installed in June) ? only render months with data or explicitly show "no data" months at zero.
Acceptance Criteria: Sum of the 12 monthly totals equals the yearly total shown.

2.8 Charts
Purpose: Visual representation of financial data (detailed in Section 21).
Description: Pie (category share), Bar (monthly/weekly comparison), Line (spending trend over time), Area (cumulative spend), Budget progress rings/bars.

Acceptance Criteria: Chart segment values always sum to 100% (± rounding tolerance of 0.1%) for pie charts; axis scales auto-adjust to data range.

2.9 Budgets
Purpose: Let users set a spending limit per category per month and get warned as they approach it.
Description: User sets a monthly amount per category (or an overall monthly budget). Dash- board and Reports show a progress bar: green (<70%), amber (70-99%), red (=100%, over budget).
User Actions: Set/edit/remove a budget per category; set overall monthly budget; en- able/disable threshold notifications.
Validation Rules: Amount required, > 0, = 999,999,999.99. A category can have only one active budget per calendar month.
Edge Cases: Budget set mid-month ? applies to the whole month retroactively for calculation purposes (spend-to-date is compared against it immediately). Category with no budget ? no progress bar shown, just raw total.
Acceptance Criteria: Progress percentage = (sum of category expenses this month / budget amount) × 100, recalculated on every relevant transaction change.

2.10 Settings
Purpose: Central place for app configuration (full detail in Section 23).
Description: Currency selection, theme (Light/Dark/System), language (stub for Phase 1, English only), notification toggles, App Lock (PIN/biometric), Export, Backup, Restore, About/Version, Reset App Data.

2.11 Dark Mode
Purpose: Reduce eye strain and respect system preference; Material Design 3 dynamic them- ing.
Description: Three modes: Light, Dark, System (default). All design tokens (see Design System) are theme-aware; toggling is instant with no app restart.
Acceptance Criteria: Every screen (including charts, dialogs, snackbars) renders correctly in both themes with WCAG AA contrast minimums.

2.12 Search
Purpose: Quickly find a specific transaction.
Description: Search bar on History screen matching notes text, category name, and amount (exact or prefix match), debounced at 300ms.
Edge Cases: Empty query ? show full list. Query matching zero results ? "No transactions found" empty state with a "Clear search" action.

2.13 Filters
Purpose: Narrow the transaction list by structured criteria (detailed in Section 22).

Description: Filter by category (multi-select), date range (presets + custom), payment method, amount range, transaction type (income/expense/all). Filters are combined with AND logic; search text is combined with active filters.
Acceptance Criteria: Applying multiple filters returns the correct intersection set, verified against a reference query over the raw dataset.

2.14 Export CSV
Purpose: Allow data portability for tax/accounting purposes.
Description: Generates a CSV with columns: Date, Type, Category, Amount, Payment Method, Notes. Scope options: current month, current year, custom range, all-time. Uses the OS share sheet to save/send the file.
Validation Rules: Must have at least 1 transaction in range to export; otherwise disabled with a tooltip explaining why.
Edge Cases: Notes containing commas/quotes must be properly CSV-escaped. Very large export (50,000+ rows) is chunsäked/streamed to avoid blocking the UI thread.
Acceptance Criteria: Exported CSV opens correctly in Excel/Google Sheets with no column misalignment, for a dataset including special characters in notes.

2.15 Backup
Purpose: Protect against data loss and enable device migration (Phase 1: manual, file-based; not automatic cloud backup).
Description: Serializes all AsyncStorage/SQLite data into a single JSON file (versioned schema), optionally shared via the OS share sheet to Drive/email/local storage.
Validation Rules: Backup file includes a schema version number and checksum for integrity verification on restore.
Edge Cases: Backup created on a newer app version than the device restoring it ? restore must handle backward-incompatible schema versions gracefully with a clear error message.
Acceptance Criteria: A backup taken immediately after adding a transaction, then restored on a clean install, reproduces identical data (byte-for-byte for records, ignoring generated timestamps like updatedAt).

2.16 Restore
Purpose: Recover data from a backup file.
Description: User picks a .json backup file via the OS file picker; app validates schema version and checksum, previews the summary (X transactions, Y categories, date range), and asks for confirmation (merge or overwrite) before applying.
Validation Rules: Reject files that fail checksum validation or have an unrecognized schema version, with a clear error and no partial write.
Edge Cases: Restoring into an app that already has data ? user must choose "Merge" (dedupe by ID) or "Overwrite" (replace all local data) - overwrite requires a second con- firmation.
Acceptance Criteria: A corrupted/tampered backup file is rejected before any data is written (all-or-nothing transaction).

2.17 Notifications
Purpose: Keep the user engaged and warn about budget thresholds (local notifications only in Phase 1 - no push server).
Description: Local, on-device scheduled notifications: daily/weekly reminder to log ex- penses (user-configurable time), budget threshold alerts (70%/90%/100% of a category or overall budget), monthly summary ready notification.
Validation Rules: Requires OS notification permission; app must gracefully degrade (in-app banner only) if permission is denied.
Edge Cases: Multiple budgets crossing thresholds the same day ? batch into a single notifi- cation rather than spamming.
Acceptance Criteria: Disabling notifications in Settings cancels all scheduled local notifica- tions immediately.

2.18 Future Features
Documented fully in Future Roadmap: Cloud Sync, OCR Receipt Scanner, Voice Input, AI Spending Analysis, Savings Goals, Bank/UPI Integration, Multi-device Sync, Widgets, Wear OS.

5. User Stories
Format: As a [persona/user], I want [capability], so that [benefit]. Grouped by module, with acceptance criteria (AC).

5.1 Onboarding & Splash (5)
1. As a first-time user, I want a short splash screen, so that the app feels polished while it ini- tializes local storage. AC: Splash shown = 2s, then navigates to Dashboard/Onboarding.
2. As a first-time user, I want a brief onboarding carousel, so that I understand the app's core value in under 30 seconds. AC: 3 slides, skippable, shown only once (flag persisted).
3. As a first-time user, I want to select my currency during onboarding, so that all amounts display correctly from day one. AC: Currency picker with search, defaults to device locale currency.
4. As a first-time user, I want to skip onboarding, so that I can get to the app immediately.
AC: "Skip" visible on every slide.
5. As a returning user, I want the app to open directly to the Dashboard, so that I don't see onboarding again. AC: Onboarding flag checked before navigation decision.

5.2 Dashboard (8)
6. As a user, I want to see my total income and expense for the current month, so that I know my financial position at a glance. AC: Values match sum of records for selected month.
7. As a user, I want to see my net balance, so that I know if I'm saving or overspending. AC:
Balance = income - expense, colored red if negative.
8. As a user, I want to see a mini pie chart of category spending, so that I instantly see where my money goes. AC: Chart updates when a transaction is added/edited/deleted.
9. As a user, I want to see my 5 most recent transactions on the dashboard, so that I don't need to open History for quick checks. AC: Sorted by date+createdAt descending.
10. As a user, I want to switch the dashboard's month, so that I can review past months without leaving the home screen. AC: Month selector persists selection during session.
11. As a user, I want to see budget progress bars on the dashboard, so that I know which categories are close to their limit. AC: Bars only shown for categories with an active budget.
12. As a user, I want to pull-to-refresh the dashboard, so that I'm confident I'm seeing the latest data. AC: Refresh indicator shown for = 1s on typical data sizes.
13. As a user with no transactions, I want a friendly empty state, so that I know how to get started. AC: Empty state includes a CTA button that opens Add Expense.

5.3 Add/Edit/Delete Expense (12)
14. As a user, I want to add an expense with amount, category, date, and payment method, so that I can record my spending. AC: Save disabled until required fields valid.
15. As a user, I want the date to default to today, so that I don't have to set it manually for same-day entries. AC: Date field pre-filled, editable.
16. As a user, I want to add optional notes to an expense, so that I remember details later.
AC: Notes capped at 500 characters with a live counter.
17. As a user, I want to pick a category from icons and colors, so that entry feels fast and visual. AC: Category grid with icon+label, single tap selects.
18. As a user, I want to edit an existing expense, so that I can correct mistakes. AC: Edit form pre-filled with existing values; save updates all aggregates.
19. As a user, I want to delete an expense, so that I can remove incorrect entries.  AC:
Confirmation dialog before permanent delete.

20. As a user, I want an undo option after deleting, so that I don't lose data from an accidental swipe. AC: 5-second undo snackbar restores the exact record.
21. As a user, I want the app to warn me (not block me) if an amount looks unusually high, so that I catch typos without being obstructed. AC: Soft warning dialog with "Save anyway"
/ "Edit" options.
22. As a user, I want to duplicate a previous expense as a template, so that recurring-like entries are faster to add. AC: "Duplicate" action pre-fills a new form with the same category/amount/payment method, today's date.
23. As a user, I want validation errors shown inline near the field, so that I know exactly what to fix. AC: Error text appears below the offending field on blur/submit.
24. As a user, I want to select a payment method, so that I can track how I paid. AC: Defaults to my last-used method.
25. As a user, I want future dates disallowed by default, so that I don't accidentally log spending that hasn't happened. AC: Date picker disables future dates unless "Allow post-dated entries" is enabled in Settings.

5.4 Add/Edit/Delete Income (6)
26. As a user, I want to add income with amount, source, and date, so that I can track money coming in. AC: Same validation pattern as expense amount.
27. As a user, I want income entries visually distinct from expenses, so that I don't confuse the two in lists. AC: Green vs red color coding, "+"/"-" prefix.
28. As a user, I want to edit an income entry, so that I can fix incorrect amounts. AC: Edits recalculate dashboard/report totals.
29. As a user, I want to delete an income entry, so that I can remove duplicates. AC: Confir- mation + undo snackbar.
30. As a user, I want to categorize income by source (Salary, Freelance, Gift, etc.), so that I can see income composition. AC: Income category picker separate from expense cate- gories.
31. As a user, I want to add notes to income, so that I remember what a payment was for.
AC: Same 500-char limit as expenses.

5.5 Transaction History (10)
32. As a user, I want to see all transactions in a scrollable list grouped by date, so that browsing feels organized. AC: Date headers "Today"/"Yesterday"/formatted date.
33. As a user, I want to tap a transaction to view full details, so that I can review or edit it.
AC: Detail screen shows all fields including timestamps.
34. As a user, I want to swipe a transaction to delete it, so that removal is fast. AC: Swipe reveals a delete action with confirmation threshold.
35. As a user, I want to search transactions by keyword, so that I can find a specific one quickly. AC: Debounced search across notes/category/amount.
36. As a user, I want to filter by category, so that I can review spending in one area. AC:
Multi-select filter chip UI.
37. As a user, I want to filter by date range, so that I can review a specific period. AC: Preset ranges (This week/month/year) + custom range picker.
38. As a user, I want to filter by payment method, so that I can see how much I spend via each method. AC: Filter combines with other active filters via AND logic.
39. As a user, I want to sort transactions by amount or date, so that I can find the largest expenses easily. AC: Sort toggle ascending/descending.
40. As a user, I want to multi-select and bulk-delete transactions, so that cleanup is efficient.
AC: Long-press enters selection mode; bulk delete confirms count before executing.
41. As a user, I want an empty state when a filter/search returns nothing, so that I know to adjust my criteria. AC: "No results" state with a "Clear filters" action.

5.6 Categories (8)
42. As a user, I want default categories pre-loaded, so that I can start tracking immediately without setup. AC: 12 default categories seeded on first launch.
43. As a user, I want to create a custom category, so that I can track spending unique to my life. AC: Name+icon+color+type required; uniqueness enforced.
44. As a user, I want to edit a category's name/icon/color, so that I can personalize it. AC:
Edits reflect immediately across all historical transaction displays.
45. As a user, I want to delete a custom category, so that I can remove ones I don't use. AC:
Prompt to reassign existing transactions to "Uncategorized."

Drag-to-reorder persists order in storage.

5.7 Budgets (8)

51. As a user, I want to set an overall monthly budget, so that I can cap total spending regardless of category. AC: Overall budget tracked independently of category budgets.
52. As a user, I want a visual progress bar for each budgeted category, so that I can see my usage at a glance. AC: Green/amber/red thresholds at <70%/70-99%/=100%.
53. As a user, I want a notification when I cross 90% of a budget, so that I can slow down spending in time. AC: Local notification fired once per threshold per month (no repeats).
54. As a user, I want to edit a budget mid-month, so that I can adjust for unexpected changes.
AC: New amount immediately recalculates progress.
55. As a user, I want to remove a budget, so that a category is no longer tracked against a limit. AC: Progress bar disappears; historical spend data unaffected.
56. As a user, I want to see which categories are over budget at a glance, so that I can take corrective action. AC: Over-budget categories surfaced at the top of the Budgets screen.
57. As a user, I want budgets to reset automatically each month, so that I don't have to re-enter them manually. AC: Budget "amount" persists as a recurring monthly setting unless explicitly changed/removed.

5.8 Reports & Charts (12)
58. As a user, I want a monthly report with category breakdown, so that I understand where my money went. AC: Category sum equals total expense for the month.
59. As a user, I want a yearly report with monthly comparison, so that I can see seasonal trends. AC: Bar chart with 12 bars (or fewer if partial year).
60. As a user, I want a pie chart of category spending, so that proportions are visually clear.
AC: Segments sum to 100% ± 0.1%.
61. As a user, I want a line chart of daily spending within a month, so that I can spot spending spikes. AC: X-axis = days, Y-axis = amount spent that day.
62. As a user, I want to compare this month vs last month, so that I know if I'm improving.
AC: % change indicator (up/down arrow, colored).

63. As a user, I want to see my average daily spend, so that I can pace myself for the rest of the month. AC: Average = total expense / days elapsed in month.
64. As a user, I want to see my top 5 spending categories, so that I know where to cut back.
AC: Sorted descending by amount.
65. As a user, I want to filter reports by custom date range, so that I can review any arbitrary period (e.g., a trip). AC: Custom range picker feeds the same aggregation engine as monthly/yearly views.
66. As a user, I want a savings rate metric (income - expense)/income, so that I can track my financial health. AC: Displayed as a percentage, handles zero-income edge case gracefully (shows "N/A").
67. As a user, I want to tap a report category to drill into its transactions, so that I can inves- tigate specific spending. AC: Navigates to filtered History pre-set to that category+date range.
68. As a user, I want to export a report as CSV, so that I can analyze it further outside the app. AC: CSV matches on-screen totals exactly.
69. As a user, I want budget-vs-actual shown on the report screen, so that I get the full budget picture in one place. AC: Progress bars mirror the Budgets screen data.

74. As a user, I want a one-tap "Clear all filters" action, so that I can reset quickly. AC:
Resets search text and all filter dimensions.

5.10 Settings (12)

76. As a user, I want to toggle Dark Mode, so that I can use the app comfortably at night.
AC: Instant theme switch, no restart.
77. As a user, I want to set the theme to "System," so that it follows my OS setting automat- ically. AC: Detects OS theme changes in real time.
78. As a user, I want to enable a PIN lock, so that my financial data is protected if someone picks up my phone. AC: PIN required on app foreground after a configurable timeout.
79. As a user, I want to use biometric unlock instead of a PIN, so that unlocking is faster. AC:
Falls back to PIN if biometrics fail or aren't enrolled.
80. As a user, I want to export all my data as CSV, so that I have a portable copy. AC: Same export engine as Reports export, scoped to "All time."
81. As a user, I want to create a backup file, so that I can protect against data loss. AC:
Backup includes schema version and checksum.
82. As a user, I want to restore from a backup file, so that I can recover or migrate my data.
AC: Preview shown before applying; merge/overwrite choice required.
83. As a user, I want to enable/disable budget notifications, so that I control how often the app alerts me. AC: Toggling off cancels all scheduled budget notifications.
84. As a user, I want to set a daily reminder time to log expenses, so that I build a consistent habit. AC: Local notification scheduled via OS scheduler at chosen time.

85. As a user, I want to reset all app data, so that I can start fresh if needed. AC: Requires typed confirmation ("DELETE") before wiping storage.
86. As a user, I want to see the app version and basic info, so that I know what I'm running.
AC: About screen shows version, build number, and licenses link.

5.11 Security & Privacy (5)
87. As a user, I want my PIN stored securely (not in plain text), so that my financial data stays private. AC: PIN hash stored via expo-secure-store, never in AsyncStorage.
88. As a user, I want the app to lock automatically after a period of inactivity, so that I don't have to remember to lock it manually. AC: Configurable timeout (immediate/1 min/5 min/never).
89. As a user, I want my backup file to not contain my PIN, so that sharing a backup doesn't expose my app lock. AC: Backup JSON excludes SecureStore-held secrets.
90. As a user, I want the app to hide sensitive content in the app-switcher preview, so that my balance isn't visible when I switch apps. AC: Privacy screen/blur overlay shown in the recents view (Android FLAG_SECURE equivalent via Expo).
91. As a user, I want confirmation before destructive actions (delete category with data, reset app, overwrite restore), so that I don't lose data accidentally. AC: Every destructive action has a distinct, explicit confirmation step.

92. As a user, I want a monthly summary notification on the 1st of each month, so that I get a recap without opening the app. AC: Notification deep-links into last month's Report.
93. As a user, I want to snooze a reminder notification, so that it doesn't nag me at a bad time. AC: Snooze reschedules for +1 hour, max 2 snoozes/day.

• Screen transitions: native stack default (slide from right on Android per platform con- vention; card modal presentation for Add/Edit sheets).

• Progress bars: animate fill on mount/update (300ms ease-out).
• Chart entrance: bars/pie segments animate in on first render only (not on every re- render, to avoid jank when scrolling triggers rerenders).
• Respect Reduce Motion OS accessibility setting - animations shortened/disabled when

9.11 Loading States
• Initial app load: Splash screen (branded, =2.5s).
• Screen-level data fetch (from local storage - should be near-instant, but always guarded): skeleton placeholders matching final layout shape (shimmer effect), not spinners, to reduce perceived latency.
• Action-level (save/delete/export/backup): button shows inline ActivityIndicator replac-
ing its label, disabled state, no layout shift.

9.12 Dark Theme
• Governed by MD3 dark tonal palette (see §9.3).
• True elevation via subtle surface-tint overlays rather than pure black backgrounds (MD3 recommendation), except OLED considerations are deferred (pure-black "AMOLED mode" is a Phase 2 nice-to-have).
• Charts re-theme axis/label colors and gridlines for dark backgrounds (no hardcoded chart colors).

9.13 Accessibility
• All interactive elements: accessibilityRole, accessibilityLabel, accessibilityHint
where non-obvious.
• Color is never the sole indicator (e.g., over-budget also shows an icon + text "Over bud- get," not just red color).
• Dynamic font scaling supported up to 130% (allowFontScaling, layouts use flex not fixed
heights for text containers).
• Focus order matches visual order for screen readers (TalkBack/VoiceOver tested).
• Minimum contrast ratio 4.5:1 for body text, 3:1 for large text/icons (WCAG AA).

9.14 Material Design 3 Application
• Uses react-native-paper's PaperProvider with a custom MD3LightTheme/MD3DarkTheme
extended with the palette in §9.3.
• Components sourced from Paper: Appbar, Card, Button, TextInput, Chip, FAB, Snackbar, Dialog, Portal, SegmentedButtons, ProgressBar, Switch, List.
• Custom components (charts, budget progress rings, category icon grid) are built to match MD3 shape/elevation/color tokens exactly, so they feel native to the design system rather than bolted-on.

11.1 Rationale per Top-Level Folder

Folder	Why It Exists

app/	Composition root - wires navigation, theme, and providers together without containing business logic itself, keeping App.tsx thin.
features/	Each feature owns its
screens/components/hooks/services, so a developer can work on "Budgets" without touching unrelated code - critical for scaling team size and codebase later.
shared/		Prevents duplication of truly generic UI/logic (e.g., an EmptyState component used by 6 different features) without letting features
become tangled with each other.
context/	Centralizes global state providers separately from features, since state (e.g., TransactionContext) is consumed by multiple features (Dashboard, History, Reports, Budgets) and shouldn't live inside any single one.



Folder	Why It Exists

storage/		Isolates all persistence concerns behind repository interfaces - this is what makes swapping AsyncStorage ? SQLite ? cloud sync possible without touching feature code (Dependency Inversion Principle).
sync/	Explicitly reserved (even if empty in Phase 1)
so the future cloud-sync feature has an obvious, pre-agreed home and interface contract (ISyncService) that repositories can later call.
assets/	Static resources, kept out of src/features to avoid bloating feature folders and to allow a single import path convention.
 tests / & e2e/	Separated from src to keep production bundle analysis clean and allow different tooling/config (Jest vs Detox/Maestro) per folder.

15. Storage Design
15.1 Phase 1 Default: AsyncStorage Structure
AsyncStorage is a flat key-value store; the app organizes it with namespaced, predictable keys and JSON-serialized arrays/objects. A StorageProvider abstraction (see folder structure
§11) means every feature interacts only with a Repository, never with AsyncStorage directly
- this is what enables the SQLite/cloud swap later without touching feature code.

Key	Value Shape	Notes

@expense_tracker/transactionsTransaction[]  (JSON  array)	All transactions in one array;
acceptable for Phase 1 scale (< ~5,000 records); see
§15.4 for the SQLite migration trigger
@expense_tracker/categories  Category[]	Seeded with 12 defaults on
first launch
@expense_tracker/budgets	Budget[] @expense_tracker/settings	Settings (single object)

Design rationale: storing each entity type as a single serialized array under one key (rather than one key per record) trades a small read/write cost (must re-serialize the whole array on every write) for simplicity and atomicity - writes can't partially fail leaving orphaned keys. This tradeoff is explicitly revisited in §15.4 as the app scales.

For users with heavy transaction volume, expo-sqlite provides indexed, queryable storage. Schema (see also Section 32 Database Schema for the full relational design used identically here and in the future backend):




15.3 Indexes


Rationale: date is indexed because every report/dashboard query filters by a date range; category_id because filtering/drilldown by category is a core interaction; deleted_at so soft- deleted rows can be cheaply excluded from all default queries (WHERE deleted_at IS NULL).

15.4 AsyncStorage ? SQLite Migration Trigger
The app monitors transactions.length on each read. When it exceeds 5,000 records (a conservative threshold well under AsyncStorage's practical ~6MB Android ceiling), Settings surfaces a one-time prompt: "You have a lot of transactions - switch to a faster storage en- gine?" Accepting runs a one-time migration (read all AsyncStorage arrays ? bulk-insert into SQLite tables ? flip a storageEngine: 'sqlite' flag in Settings) via the shared Repository interface, so feature code is entirely unaware of which engine is active.

15.5 Caching
• In-memory cache lives in the relevant Context (e.g., TransactionContext holds the full in-memory array after first load) - this is the cache; repositories are only re-read from disk on app cold start or explicit invalidation (e.g., after Restore).
• Computed aggregates (dashboard totals, report breakdowns) are not cached beyond Re- act's own memoization (useMemo) - recomputing from the in-memory transaction array is fast enough (see performance targets in NFRs) that a separate cache layer would add complexity without measurable benefit at Phase-1 scale.

15.6 Backup & Restore Strategy Backup file format (.json):







}



• Checksum: SHA-256 hash of the serialized data object, computed at export time and verified before any import write - protects against corrupted or tampered files.
• Schema version: every backup embeds the schema version it was created under. On restore, if backupSchemaVersion < currentSchemaVersion, the same migration runner used for in-place app updates (§15.7) is applied to the backup's data before import, so old backups remain restorable indefinitely.
• Merge vs. Overwrite: Merge deduplicates by id (backup records with an id not present locally are added; conflicting ids keep whichever has the later updatedAt - last-write- wins, the same rule reserved for future cloud sync). Overwrite wipes local data first, then imports, behind a double confirmation.
• Atomicity: the entire restore is staged in memory and validated fully before a single write batch is committed - a failure partway through never leaves the app in a half- restored state.

15.7 Migration Strategy (Schema Evolution)
• Every stored entity set is versioned via the single @expense_tracker/schema_version key.
• On app start, a MigrationRunner compares stored version to the app's current ex- pected version and applies an ordered list of migration functions (migrateV1toV2, migrateV2toV3, ...), each a pure function transforming the old shape to the new one.
• Migrations are additive-first (new optional fields default safely) to minimize breaking changes; destructive migrations (field removal/rename) always ship with a data- preserving transform, never a silent drop.
• Migration runs are logged (development builds) and covered by dedicated unit tests per migration step (see Testing Strategy).

16.5 Redux Toolkit - Explained as an Alternative
While Context API is sufficient for Phase 1's state complexity (a handful of entity collections, no deeply nested or high-frequency updates), Redux Toolkit (RTK) is documented here as the recommended alternative if the app's state grows significantly (e.g., after adding cloud sync with optimistic updates, offline queues, and complex conflict resolution).
When to migrate to RTK: - State updates become frequent enough that Context's "any consumer re-renders on any state change" behavior causes measurable performance issues (Context does not support selective subscriptions the way Redux + useSelector does). - Sync/offline-queue logic needs robust, testable, time-travel-debuggable state transitions. - The team wants strong DevTools support for debugging complex state interactions.
How it would map:

CategoryContext	categoriesSlice
BudgetContext	budgetsSlice
Repository calls inside context actions	RTK Query endpoints or createAsyncThunk
wrapping the same Repository classes (repositories stay unchanged - only the state-management layer above them swaps out)



Context (Phase 1)	RTK Equivalent

Manual useMemo selectors	createSelector (Reselect, bundled with RTK) for memoized derived data (e.g., monthly totals) with fine-grained re-render control


Design rationale for deferring RTK: introducing Redux's boilerplate (slices, store setup, provider) for an app whose Phase-1 state is five flat collections would be premature complexity. The Repository abstraction (§15) means this is a state-management-layer-only swap later
- business logic in reportEngine, budgetEngine, and all repositories remains 100% reusable regardless of which state library sits above them.

19. Business Logic
All formulas live in pure, unit-tested functions in reportEngine.ts and budgetEngine.ts (fea- ture services/ folders), decoupled from React so they're trivially testable and reusable if the state-management layer changes (§16.5).

19.1 Monthly Totals
totalIncome(month) = S amount WHERE type='income' AND date in month AND deletedAt IS NULL totalExpense(month) = S amount WHERE type='expense' AND date in month AND deletedAt IS NULL netBalance(month)	= totalIncome(month) - totalExpense(month)

19.2 Yearly Totals
totalIncome(year)	= S totalIncome(month)	for month in year's 12 months totalExpense(year) = S totalExpense(month) for month in year's 12 months
Computed by re-using the monthly function across 12 iterations rather than a separate yearly query path - guarantees monthly and yearly figures can never drift out of sync.

19.3 Category Totals
categoryTotal(categoryId, period) = S amount WHERE categoryId = categoryId AND date in period AND categoryPercentage(categoryId, period) = categoryTotal(categoryId, period) / totalExpense(period)
Guard: if totalExpense(period) === 0, all percentages are reported as 0, not NaN.

19.4 Budget Calculations

24. Error Handling Strategy
24.1 Storage Errors
• Every Repository method wraps its AsyncStorage/SQLite call in try/catch, throwing a typed StorageError ({ code, message, cause }) rather than letting raw native errors bubble up.
• UI layer catches StorageError and shows a generic, non-technical Snackbar ("Couldn't save your changes - please try again"), while the raw error is logged (dev builds: con- sole; production: reserved hook for Sentry/Crashlytics, see §24.6).

• Read failures on app start (corrupted key) trigger a ScreenError fallback with a "Retry" button before assuming full data loss; only after repeated failure does the app offer "Reset this data" as a last resort, never automatically.

24.2 Invalid Input
Handled entirely at the form layer (see Validation Rules) - invalid input never reaches the storage layer; Repository.create()/update() also re-validate defensively (defense in depth) and reject with a clear error if somehow called with invalid data (e.g., from a future automated import feature).

24.3 Data Corruption
• Each stored JSON blob is wrapped with a lightweight envelope ({ version, data }); on parse failure, the app does not silently reset that key - it flags the key as cor- rupted, keeps other keys intact, and surfaces a targeted recovery screen: "Your [Trans- actions/Categories/Budgets] data couldn't be read - restore from a backup or start fresh for this data only?"
• This per-key isolation means, e.g., corrupted Budgets data never takes down Transac- tions or Categories.

24.4 Backup Failures
• Failure to generate the export file (e.g., serialization error, disk full) ? Snackbar with "Couldn't create backup - please try again," no partial file left behind (write to a temp path, only move/share on full success).

24.5 Import Failures
• Checksum mismatch, unrecognized schema version, or malformed JSON ? rejected be- fore any write, with a specific, honest message (not a generic "something went wrong")
- see Section 2.16 and Backup Strategy.
• Partial-import prevention: the entire restore is staged and validated in memory; the actual storage write is a single atomic batch operation.

24.6 App Crashes
• A root-level ErrorBoundary (React) catches render-time errors app-wide as a last resort, showing a "Something went wrong" screen with "Reload App" - but per-tab Error- Boundarys (see Component Architecture) catch most errors before they reach the root, so one broken screen doesn't take down the whole app.
• Native crashes (outside JS's ErrorBoundary reach, e.g., a native module fault) are out of JS's control; the architecture reserves a hook for Sentry/Crashlytics SDK integration (not included in Phase 1 to keep the app fully offline/zero-third-party by default, but the interface - a single crashReporter.logError() call site used throughout the error- handling code - is already in place so enabling it later is a one-line config change, not a refactor).

24.7 Recovery Methods



Failure	Recovery Path

Corrupted single data key	Targeted per-key recovery screen ? restore from backup or reset that key only
Failed restore	Rejected pre-write; user retains their existing data untouched
Repeated storage read failure	"Reset this data" as an explicit,
clearly-labeled last resort (never automatic)

25. Security
25.1 Data Encryption
• Phase 1 does not encrypt the bulk transaction/category/budget data at rest beyond what the OS provides by default (Android's app-sandboxed storage), since this is a local-only, single-user app with no data leaving the device - full at-rest encryption of AsyncStor- age/SQLite is documented as a Phase 2 hardening step (e.g., via expo-sqlite with SQL- Cipher or react-native-encrypted-storage) once cloud sync introduces higher stakes for data-at-rest protection.
• Secrets are the exception: the App Lock PIN (hashed, never plaintext) is stored via expo-secure-store, which uses the OS Keychain (iOS) / Keystore (Android) - hardware- backed encryption, isolated from the general app storage.

25.2 Secure Storage
expo-secure-store is used exclusively for: PIN hash, biometric-enabled flag salt (if needed by the hashing scheme). General app data (transactions, categories, budgets, settings) stays in AsyncStorage/SQLite since it doesn't warrant Keychain-level storage overhead and volume limits.

25.3 Backup Security
• Backup JSON files explicitly exclude anything from SecureStore (PIN hash) - a shared/lost backup file can never expose the App Lock secret.
• Backup files are not encrypted by default in Phase 1 (since they may be intentionally shared/emailed by the user for migration) - documented as a Phase 2 option: "Encrypt backup with a passphrase."

25.4 PIN Lock
• 4 or 6-digit PIN, hashed (not reversibly encrypted) using a standard hashing approach suitable for React Native (e.g., SHA-256 with a device-generated salt, both stored in SecureStore).
• 5 consecutive failed attempts ? 30-second lockout, escalating on repeated failure sets, to deter brute-force without permanently locking a legitimate user out.

25.5 Biometric Authentication
• expo-local-authentication used to trigger Face ID / Fingerprint / device biometric prompt.
• Biometric is always an alternative unlock method layered on top of the PIN (the PIN re- mains the recoverable fallback) - never the sole credential, since biometric enrollment can change or fail on some devices.

25.6 Privacy
• "Hide content in app switcher" - a privacy overlay (blurred logo screen) shown when the app is backgrounded, so financial figures aren't visible in the OS recents/app-switcher preview.
• No analytics, ads, or third-party SDKs are included in Phase 1 by design (see Project Overview §1.6/1.7) - nothing to configure for privacy compliance because nothing is collected.

• Versioned under /api/v1/ from day one to allow non-breaking evolution.

The relational schema mirrors the SQLite schema in Storage Design §15.2 so that a future backend (PostgreSQL, for example) can reuse the same shape, easing the sync layer's mental model. Backend-specific additions below (multi-user support):
-- Backend adds a users table and a user_id FK absent from the local-only schema
CREATE TABLE users (
id UUID PRIMARY KEY,
email TEXT UNIQUE NOT NULL,
password_hash TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL, updated_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE categories (
id UUID PRIMARY KEY,
user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE, name TEXT NOT NULL,
type TEXT NOT NULL CHECK (type IN ('expense','income')), icon TEXT NOT NULL,
color TEXT NOT NULL,
is_system BOOLEAN NOT NULL DEFAULT FALSE, is_archived BOOLEAN NOT NULL DEFAULT FALSE,
sort_order INTEGER NOT NULL DEFAULT 0, created_at TIMESTAMPTZ NOT NULL, updated_at TIMESTAMPTZ NOT NULL, UNIQUE (user_id, name, type)
);

CREATE TABLE transactions (
id UUID PRIMARY KEY,
user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
type TEXT NOT NULL CHECK (type IN ('expense','income')), amount NUMERIC(12,2) NOT NULL CHECK (amount > 0),
category_id UUID NOT NULL REFERENCES categories(id), category_name_snapshot TEXT NOT NULL,
date DATE NOT NULL,
payment_method TEXT NOT NULL, notes TEXT,
is_recurring BOOLEAN NOT NULL DEFAULT FALSE, attachment_uri TEXT,
deleted_at TIMESTAMPTZ, created_at TIMESTAMPTZ NOT NULL, updated_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE budgets (
id UUID PRIMARY KEY,
user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
category_id UUID REFERENCES categories(id), amount NUMERIC(12,2) NOT NULL CHECK (amount > 0), month CHAR(7) NOT NULL, -- 'YYYY-MM'
notify_at_70 BOOLEAN NOT NULL DEFAULT TRUE, notify_at_90 BOOLEAN NOT NULL DEFAULT TRUE,

37. Coding Standards
37.1 TypeScript Guidelines
• strict: true in tsconfig.json; no implicit any.
• Prefer interface for object shapes (data models), type for unions/utility compositions.
• No // @ts-ignore without an inline comment explaining why; prefer proper typing or a narrow, documented exception.
• All async functions have explicit return types (Promise<Transaction>, not inferred).

37.3 Folder Naming
All lowercase, kebab-case for multi-word folders (backup-restore/), matching the structure in Section 11.

37.4 File Naming
Component files match their default export name exactly (DashboardScreen.tsx exports Dash- boardScreen); one primary component per file; co-located *.styles.ts only if styles exceed
~40 lines (otherwise inline StyleSheet.create).

37.5 Component Naming
Screens end in Screen (AddTransactionScreen), reusable UI components are noun-based with- out a suffix (AmountInput, BudgetProgressBar), wrapper/provider components end in Provider (TransactionProvider if extracted separately from TransactionContext).

37.6 Hooks
One responsibility per hook; hooks that wrap Context consumption are named use<Feature> (useTransactions() reading TransactionContext), while computation-heavy hooks are named for what they compute (useMonthlyAggregation), not what they consume.

37.7 Testing
Test files co-located under  tests / mirroring src/ paths; naming: <subject>.test.ts. Ev- ery service/repository/utils file has a corresponding test file before being marked complete (enforced via PR review checklist, not tooling, in Phase 1).

37.8 Linting & Formatting
ESLint (with @typescript-eslint,  eslint-plugin-react-hooks,  eslint-plugin-react- native) + Prettier, run via a pre-commit hook (husky + lint-staged) so formatting/lint issues never reach CI in the first place.

37.9 Git Workflow
• Trunk-based-ish with short-lived feature branches:	feature/<short-description>, fix/<short-description>, chore/<short-description>.
• PRs require: passing CI, at least one review, no unresolved conversations.
• main is always deployable (staging build triggers automatically per §27.6).

37.10 Commit Messages
Conventional Commits format: type(scope): summary, e.g., feat(budgets): add threshold notification scheduling, fix(history): correct filter AND logic for amount range. Types: feat, fix, refactor, test, docs, chore, perf.

39.1 Glossary

Term	Definition

Offline-first	An architecture where the local device is the primary source of truth, and network sync (if present) is an enhancement, not a requirement, for core functionality
Repository Pattern	A design pattern abstracting data access behind an interface, decoupling business/UI logic from the specific storage technology used
Last-write-wins	A conflict-resolution strategy where, on a sync conflict, the record with the most recent updatedAt timestamp is kept
Soft delete	Marking a record as deleted (via a deletedAt field) without immediately removing it, enabling undo functionality

Denormalization		Storing a redundant copy of related data (e.g., categoryNameSnapshot on a Transaction) to preserve historical accuracy even if the source record later changes
